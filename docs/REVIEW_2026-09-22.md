## 优先处理的发现

### 1. [P1] 后台地区可以 ready，但第一次进入必然失败

位置：`engine/world.py:262-275,324-335`、`engine/gameplay.py:223-224`、`engine/runtime.py:140`。

地区校验编译几何和引用，只有开局 `r0` 在安装时执行 `enter`。其他地区先标记 ready，玩家真正到达时才执行进入钩子。一个包含 `div(1,0)` 的进入钩子在声明变量后通过完整安装；实际沿地图移动到门口并交互，得到 `RuleError: division by zero`，事务正确回滚到 `r0`，但目标地区仍然 ready。

因此目前的回滚保护了存档，却没有提供内容故障恢复。该错误发生在玩家动作而非生成任务中，导演失败列表没有对应条目，现有重试入口也无法修复这个 ready 地区。玩家会反复进入、反复失败。

建议给地区发布增加隔离执行关卡：使用真实 Runtime 在世界副本执行 `enter`、一次移动或等待，并对可用动作验证基本执行条件。静态拒绝常量除零、明显类型不匹配等确定错误。玩家动作发生内容错误时保留原状态，把内容 ID、JSON 路径、输入状态与异常送入专门的内容修复流程；尚未成功进入的地区可以退回待修复状态。

验收应包括“后台安装成功—实际进入失败—修复—再次进入成功”，并确认没有重复奖励、人物状态变化或存档污染。

### 2. [P1] 有旗标生产者不等于目标存在完成路径

位置：`engine/world.py:214-223`、`engine/campaign.py:61-75`、`engine/scene.py:121-153`。

当前章节校验检查结构连通、开局有一条可用路线、必要旗标在某处被写入；地区几何检查按地表判断可达性，允许动态门作为谜题。它们都没有证明门、资源、任务和动作条件之间存在有效完成顺序。

复现将结局旗标 `letter` 的唯一生产动作改为“当 `chapter.letter` 为真时把它设为真”，初始值为假。四个地区均通过校验并标记 ready，完整图也合法，但完成目标没有可执行的起点。只检查引用和生产者集合无法发现这种简单自锁。

建议先覆盖可判定的常见子集：旗标生产和消费依赖、钥匙与门、单向路线、有限资源余额，以及任务的互斥/失败条件。用有界状态搜索产出一条实际可回放的完成路线，同时检查关键分支。超出搜索预算时标记“未证明”，不能据此宣称无解，也不能显示已验证可通关。

模型可以提交预期解法作为候选轨迹，由本地运行时从真实初始状态逐步验证。该轨迹不能直接授予物品或设置完成旗标。先实现明确自锁和跨区钥匙循环检查，收益会高于继续扩大可生成规则种类。

### 3. [P1] 双路任务最终失败会丢弃成功组件，并漏记其用量

位置：`engine/region_pipeline.py:170-197`、`engine/director.py:276-290,529-541`。

两路结果先通过 `future.result()` 同时取得，再汇总 usage。任一路最终抛异常时，另一条成功结果尚未进入 `usages`，也没有成为持久化续作输入。Director 对 provider failure 不保留 `failed_payloads`。当前组件内部传输补试可以保留另一分支，但补试耗尽、手动重试或进程重启后仍会丢失成果。

模拟玩法成功、视听失败，调用两次地区生成，玩法和视听都请求了两次。失败上报只有视听的 11/7 tokens，玩法已经消耗的 100/50 tokens 未进入任务汇总。实际损失是重复等待、重复额度和偏低的用量统计。

建议在每条真实请求完成时立即记录 usage 与原始结果；持久化组件状态，以世界 epoch、地区依赖摘要、协议版本、prompt 版本和组件种类作为续作键。下一次只请求失败或依赖已经失效的组件。错误对象也要携带已成功组件和聚合用量；未知用量保留为未知。

这是速度与稳定性收益都很直接的改进。验收要覆盖“两路中任一路失败”“成功后进程重启”“约定变化后旧组件失效”三种场景。

### 4. [P2] 非法 JSON 无法进入现有组件修复

位置：`engine/region_pipeline.py:199-213`。

`repair()` 在组织修复输入时先对 `responses[component]` 再调用 `parsed()`。若原错误恰好是非法 JSON，修复输入尚未发给模型就再次抛异常。复现让视听返回 `{`，即使 `_region_can_repair()` 为真，仍只有初始两次请求，修复请求数为零，已发生用量也没有正确附在这个异常上。

建议修复输入允许携带有长度限制的原始字符串，明确附带解析错误、组件名和已有约定。合法 JSON 才使用对象形式。两条组件各自保留独立修复预算，避免第一条修好后发现第二条错误就直接放弃整个任务。

### 5. [P2] 双路约定没有覆盖音频引用，容易退回整区修复

位置：`engine/region_pipeline.py:42-73,142-155,215-225`、`engine/runtime.py:411-419`、`engine/gameplay.py:54-56`。

共享约定定义了图形槽、地表和持续人物，却没有定义玩法可以使用的 `sound/music` cue，也没有向视听作者提供新创作对象的 ID。玩法能生成 `op:sound`，视听也被允许输出按对象绑定的 `audio.objects`，这两类跨分支引用没有明确的共同来源。

复现让玩法引用 `gate_open`，视听只提供探索音乐：两路组装成功、`parse_patch` 成功，直到世界引用校验才报 `undefined audio cue`。这类错误会进入外层整区修复，丢掉组件修复的速度优势。

建议在本地约定中加入有界语义 cue、对象绑定规则及各字段的责任方；引用校验返回可定位到组件的诊断。新增临时对象的音效可以由玩法提交语义绑定要求，再由本地已有 cue 映射或小范围补充视听完成。不要通过删掉失败音效来冒充修复成功。

### 6. [P2] 资源“伤害”和“支付代价”共用扣减，漏写前置条件即可免费使用

位置：`engine/game_spec.py:52-59`、`engine/runtime.py:169-184,227-231`。

资源扣减目前夹在 0 与上限之间。这个行为适合伤害和环境消耗，但当模型把同一个操作用于交易或技能费用时，必须另外正确生成余额条件。物品负数扣减则会在余额不足时抛错，两种支付方式行为不一致。

复现从 0 点专注开始，加入“花费一点专注调查”，效果为 `resource -1` 再增加调查次数，没有 `when`。内容通过校验，连续两次正常 invoke 均成功，余额一直为 0，调查次数为 2。文字上的代价没有形成规则约束。

建议显式增加 `costs` 或受限 `spend` 语义：先检查完整支付能力，再原子扣除和执行；伤害继续使用原有资源变化。界面可用状态和代价展示从同一份声明生成。同时对重复奖励设置 once、冷却、库存或总收益约束，检查零成本刷取循环。

### 7. [P2] Jev 审查仍在交付关键路径，并且不服从剩余总时限

位置：`engine/director.py:515-523`、`engine/semantic_review.py:63-66`、`engine/jev_judgments.py:33-37,56-64,131-133,181-183`。

当前内容审查在完整硬校验后同步执行，完成后才 `_deliver`。它不否决内容，但仍推迟 ready，而且整个双路任务占用调度容量直到它返回。Jev 接口只接收取消事件，没有接收任务 deadline；固定请求与重试超时可能使临近 deadline 的任务继续等待。

历史成功任务中“请求＋记录的校验”以外还存在约 1.46～2.00 秒尾部时间，包含 Jev、应用和记账，不能全部归因为 Jev；当前没有足够的阶段计时来拆开。另一个统计问题是 SDK 调用后失败会返回 `requests=0`，SDK 内部重试也没有独立计量。

建议将观测型语义审查放入独立、有界队列，以已校验内容哈希绑定结果；只有明确阻断发布的检查留在关键路径。若保留发布前审查，就必须传入剩余 deadline、明确超时降级并测量其收益。为 Jev 单列实际请求尝试、失败、缓存命中、耗时和未知 tokens。

Jev 已经把同一状态的独立问题合并请求，无需再做一次“批处理改造”。下一步是压缩重复证据、复用稳定判定，并把运行时实际效果轨迹提供给审查器。当前每个 unit 重复附带 objectives、definitions 和相关 hooks，证据量会随动作数增长。数值支付和可达性由代码验证，Jev 更适合检查玩家提示与已经观察到的结果是否一致。

TypeSafe 官方资料也建议把独立问题一次发出、由代码选择适用结果，并用业务样本校准置信阈值：[并行问题模式](https://docs.typesafe.ai/patterns/fan-out)、[置信度说明](https://docs.typesafe.ai/confidence)。置信度不能作为整章可通关证明。

### 8. [P2] 双路地区独占调度，重要剧情响应与紧急出口可能长期等待

位置：`engine/director.py:336-383,399-407`、`engine/world.py:123-135`。

`_next_job()` 在检查等待出口和导演复盘前，先因为任何在途 pipeline 直接返回 None。双路地区确实保护了两次请求的并发上限，但同时把整个逻辑任务当成不可拆的占位。等待中的另一出口、任务反应和重要复盘都会排队；当前地区有多个相邻缺口时，下一次调度又先选择相邻地区。

反应任务仍以全局 `story_revision` 严格判旧。玩家在模型思考期间继续做选择，旧反应可能完整生成后被丢弃。已有地区依赖摘要和复盘事件批次是正确基础，可以把相同思路逐步用于局部反应，而不能直接去掉一致性检查。

建议分开“逻辑制作任务”与“实际模型请求”，用统一的请求容量控制，加上等待出口、主线进展、当前反应、邻区准备、远端装饰的优先级。优先级在请求开始和分支完成边界生效；已经占用的请求容量不能承诺立即抢占。保留成功分支后，下一次有空位可以先服务玩家当前需求。

预取从固定两跳进一步升级为按需排序：结合当前目标、已揭示路线、实际位置、锁门前置和预计可达时间。相邻不代表马上可玩；隐藏且暂不可解的地区可以降低优先级。衡量“玩家进入出口时命中准备内容的比例”，同时统计未使用预取和过期请求。

### 9. [P2] 本地编排热点是深拷贝与全量快照

位置：`engine/gameplay.py:8-14,134-149`、`engine/world.py:415-435`、`engine/server.py:94-107,130-165`、`client/main.gd:1182-1187`。

每次事务先深拷贝完整 state 和最多六张缓存地图。`snapshot()` 对当前地区复制后，在最终返回时又复制整个快照；每件有自定义 use 的物品在检查可用性时还复制当前地图。空事务也会付出这笔成本。

本次最终单独执行的本地小样本如下。快照各 50 次，wait 各 30 次，单位毫秒；数据来自独立存档副本，不含 HTTP 和渲染。

| 存档样本 | 缓存地区数 | 快照 JSON 字节 | 快照＋编码 p50 / p95 | 空事务 p50 | 正常 wait p50 / p95 |
|---|---:|---:|---:|---:|---:|
| 两路夜市样本 | 1 | 37,473 | 7.91 / 9.81 | 5.17 | 14.65 / 19.12 |
| Jev 试玩样本 | 2 | 44,564 | 8.65 / 11.94 | 8.20 | 14.78 / 16.46 |
| 较长试玩样本 | 5 | 54,899 | 33.73 / 38.33 | 35.88 | 42.24 / 68.15 |

不同存档的动作、物品和规则也不同，不能只把差异归因为地图数量。对较长样本的独立 cProfile 中，50 次快照加空事务总计 17.816 秒，deepcopy 累积占 17.581 秒；这是分析器开销下的占比证据，不能当作真实动作延迟。

客户端每 0.45 秒拉取 `/state`，动作回复也返回全量快照。三份样本每次 37～55 KB；即使静止也重复传地图、绘图配方、规则与场景定义。服务端还在世界锁内编码并写 socket，慢读取和大快照会拖住其他动作与生成提交。

建议先把静态地区定义和动态玩家/对象状态分开；用地区内容哈希、几何版本和状态版本按变化投影。物品条件改为真正只读的 evaluator，同一次快照共享只读视图。事务改成复制本次受影响状态或写集日志，保留 SQLite 原子提交及完整回滚语义。先准备一致快照，再在锁外编码和发送。单纯换 JSON 库不会解决深拷贝成本。

### 10. [P3] 客户端准备提示引用了“到访数”

位置：`client/ui/game_hud.gd:216-219`、`engine/world.py:434`。

HUD 用 `map_count` 增长触发“新地区已经准备好”，但后端 `map_count` 实际是 visited 地区数。后台准备完成不会触发这条通知，玩家真正进入后反而才出现。

建议根据前沿 ready 状态的变化或明确的地区发布事件通知，并只展示玩家已经知道的路线。这个改动很小，却能让预取成果对玩家可见。当前地图每帧重绘、HUD 每帧更新和每次快照重新计算地表展示也有优化余地，但本次没有实际 GPU 帧时间证据，应在真实客户端测量后再决定缓存地表层或使用 TileMapLayer。

## 提升可玩性的实现方向

**把每个地区的玩法要求变成可以验收的约定。** 导演现有委托包含人物、技能、任务和收益上限，可以增加入口条件、至少一条主线完成轨迹、可选分支、消耗来源、失败恢复方式以及明确的跨区后果。验证器应证明关键规则落实，文字稿再负责人物动机和氛围。

**让选项造成可区分的状态变化。** 自动比较不同选项的结果：是否影响资源、路线、关系、风险或后续可用动作；识别只换一句对白但结果完全相同的伪分支，以及总是更好且没有代价的支配选项。纯叙事选择可以保留，不应强迫每句对白都发奖励，但关键选择需要兑现设计承诺。

**战斗用短模拟检查平衡。** 从真实资源状态执行合法技能，检查能否造成伤害、是否出现无限恢复、弹药是否足够、是否存在撤退/交涉路径，以及敌人行动有没有可理解的预告。当前验证“至少有一个 combat action”和敌人行为存在，还不够保证战斗值得玩。用多个简单策略比较收益和风险，避免把同一最优按钮重复按到底。

**把失败设计成可继续的后果。** 关键物品用尽、人物死亡、支线互斥或资源不足之后，应有明确的可恢复路径或明确终局。不要让玩家面对所有按钮不可用而没有解释的界面。内容运行错误与角色在规则内失败要使用不同恢复流程。

**长期记忆按因果检索。** 当前 `memory()` 截取最近 16 个人物/技能、24 个任务，`director_context()` 截取 12 个事件；更早且仍未兑现的承诺可能不在输入里。已知事实保存在权威账本，按当前地区、任务依赖、持续人物和未兑现后果检索，再补最近事件。记忆摘要不要覆盖规则事实。也要把重复检查、往返、无进展时间等信号提供给导演，帮助发现卡关和节奏问题。

**原创内容继续保留在高价值部分。** 地形铺设、素材合法性、数值计算和通用规则由本地模块完成；模型重点创作目标、人物冲突、关键选择和少量辨识度高的物件。当前模块、材质和点缀已经具备，可以进一步减少无用图形槽以及必须生成但实际未使用的装饰。新的地区层级/对象简报若要增加模型轮次，需要证明减少修复能覆盖新增等待。

## 生成速度的下一步实验

首个可玩地区的关键路径大致为：

```text
章节规划
  → max(玩法生成, Jev 素材选择 + 视听生成)
  → 组件/整区修复
  → 硬校验
  → Jev 内容审查
  → 事务安装与客户端准备
```

先减少失败后的重做，再缩短首批内容规模和正文输出。当前 prompt 已经做了投影、紧凑 JSON、材质复用和缓存 key，不能把这些列成尚未实现的新功能。缓存 key 已存在而旧日志命中为零，下一次线上实验应核对实际 cache usage、输入顺序和服务行为，不能预设缓存收益。

在完成组件续作之后，可以试验分阶段发布。第一阶段交付完整、可执行的开局玩法与足够的题材视听，后续生成可选内容。每个阶段都要有独立协议、校验和提交，保持已发布的碰撞、对象身份、任务条件不被后台改写。原始 JSON 流的一部分不能直接进入游戏状态。

对于地区规划，优先比较“现有滚动规划”与“更小但保留跨区依赖的开局约定”，同时记录后续连贯性和扩图重写率。直接削减所有上下文或降低思考等级，可能只是把等待转移到修复阶段；应以相同任务和相同质量门槛比较总等待。

## 落地顺序与验收指标

| 顺序 | 工作 | 预期收益 | 主要风险与验收 |
|---|---|---|---|
| 第一批 | 非法 JSON 修复、每请求用量记录、成功组件续作、音频引用约定 | 直接降低重试浪费和长尾等待 | 错误复用旧组件；使用依赖哈希和协议版本，测试单支失败及重启 |
| 第一批 | 进入钩子试运行、内容错误修复入口、简单自锁检查 | 防止“ready 但进不去/无法完成” | 测试副本与正式行为不同；必须复用同一 Runtime 和动作入口 |
| 第二批 | 显式支付、重复奖励检查、关键目标轨迹回放 | 降低免费技能、刷资源和卡关 | 保留伤害/环境消耗语义，覆盖不足支付和事务回滚 |
| 第二批 | Jev 异步观测、请求级队列、局部反应依赖 | 降低玩家等待和过期生成 | 后台结果污染当前状态；发布内容哈希、批次确认和容量上限必须保持 |
| 第二批 | 静动态快照、只读 evaluator、缩小事务复制范围 | 缩短长存档动作延迟和降低后台 CPU | 回滚或客户端乱序回归；保留故障注入与版本检查 |
| 第三批 | 分阶段开局、因果记忆、战斗模拟与内容质量评分 | 提升完整游玩的连贯性和重玩价值 | 协议改动大；先对有限语料和完整章节验证 |

建议建立按题材、任务复杂度和 provider 分组的固定评测集，同时保留失败样本。在线对照采用相同输入、固定请求预算，分开报告首次生成、组件修复、完整重写和回放结果。至少测以下指标：

- 速度：从创建世界到能进行首个有意义操作的 p50/p95；出口等待时间；首次输出与完整输出时间；每个通过验收的地区请求数和总 tokens。
- 编排：预取命中率、未使用预取比例、过期结果比例、重要剧情响应等待时间、Jev 各阶段耗时。
- 稳定性：首遍验收通过率、组件修复恢复率、动作运行异常率、已提交动作去重、进程中断后恢复率。
- 可玩性：在固定初始状态下主线能否完成、各关键分支能否继续、零进展循环、资源套利、战斗策略差异以及玩家提示和实际效果一致性。
- 本地性能：动作 HTTP p50/p95、快照生成与字节量、世界锁占用，以及真实客户端帧时间。

第一阶段的完成标准应是上述已复现缺陷都有回归保护，成功组件可在失败与重启后复用，并且代表性章节有一条正常动作完成轨迹。待这一基线稳定后，再用在线实验决定分阶段生成是否值得实施。
