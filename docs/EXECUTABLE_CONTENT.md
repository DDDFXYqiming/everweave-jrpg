# Content Runtime v2：模型创作的是可执行内容

章节与游戏规格已在地区 DSL 上方接入，完整规划协议见 [CAMPAIGNS.md](CAMPAIGNS.md)。本文说明局部场景及其规则执行。

## 地区能表达什么

在线新区域必须包含 `scene`、`program`、`visuals`。缺少它们会进入原有的最多一次修复，不能悄悄退回旧 PCG 地图。旧存档和显式离线自检保留原逻辑。

- **空间**：模型声明地图尺寸、房间、边界、门、路和对象锚点；施工器直接执行，不自动挖出一张中心辐射道路图。支持原创建筑占地、实心物体与可进入的房间。室内是同地图房间，不是完整楼层编辑器。
- **行为**：模型声明状态、表达式、操作、事件处理器和目标条件。不是再增加几个“护送/解谜”任务枚举。
- **画面**：模型生成像素几何、可选动画帧、地表纹理；`scene.paint.surface` 真正参与地面渲染。实体可以拥有独立图形与碰撞占地，重要对象应显式指定 `sprite`。新地区可以省略主角配方，沿用同一个人的外观。
- **实时改变**：`reaction.paint`、`object_updates`、新增 `visuals` 和新增 `program` 可以共同修改已进入区域。不能把过去改写掉，但允许玩家行为导致门打开、道路改变、对象换形等现时后果。
- **去重复**：上下文增加空间、交互和图形设计摘要以及结构签名；名字变化不会改变任务的逻辑签名。相似内容给提示并反馈给后续导演，不增加无限重试。这是去重复辅助，不是原创性或审美质量证明。

## 输入与操作

正常启动脚本不变。在线新世界先生成章节与游戏规格，再使用 v2 地区 DSL；本轮以新存档为验证入口，不提供旧世界转换验收。

`E` 操作相邻对象；`F` 显示此刻可执行的自定义操作；`.` 等待一个行动 tick。战斗出现模型定义的技能按钮，用 `1`～`9` 选择，`Esc` 撤离。旧存档的旧战斗仍保留原来的按钮。

## 可执行语言

准确协议在 `engine/content.py`（验证）、`runtime.py`（执行）和 `content_prompt.py`（给模型的完整说明）里，三者共同定义边界。模型不输出 Python、GDScript 或资源路径。

`program` 含 `vars`、`actions`、`hooks`、`objectives`。章节世界额外支持读取 `{get:"chapter.FLAG"}` 和 `{get:"resources.ID"}`，使用 `{op:"chapter",key:FLAG,value:EXPRESSION}` 写共享旗标，使用 `{op:"resource",id:ID,delta:EXPRESSION}` 改资源。旗标须先在章节声明，资源须在游戏规格启用。

动作条件是表达式树，可以读取角色、当前战斗、区域变量、对象状态、物品数量、事实和最近位置历史；动作效果可以修改自定义状态、受限数值、物品、对象位置、形状、实心状态和地表，也可以发信号、设置行动计时器。多个条件和历史状态可以组成全新的谜题，而无需引擎包含该谜题的专用函数。

钩子支持进入、移动、等待、交互、选择、战斗回合和自定义信号。目标用任意受支持的布尔表达式决定完成或失败，奖励仅执行一次。执行结果和计时器保存到地图存档。

所有常规操作和已经编译的规则在本机运行。LLM 创作规则，不逐步替代解释器执行；因此不会为影子每走一步再请求一次模型。

### 举例：两步之前的影子

模型用 `move` 钩子，将某对象的位置设为 `{history:2,field:"x"}` 和对应的 `y`。再用一个条件表达式判断玩家和影子是否分别站在指定区域，改变门的 `solid` 和 `sprite`。**引擎没有 shadow_puzzle 这个玩法模板。**同一套通用语法也可表达压力、顺序、资源交换和回合条件。

这个例子在 `tests/content_fixtures.py`，只供验收，不被在线生成导入。

## 一致性与安全

玩家动作、触发器、奖励和地图变化一起原子提交；任何一项失败都回滚内存与 SQLite。输入、已有事实、库存和地图连接不开放为任意路径写入。模型程序无文件、网络、导入或 eval 权限。

表达式深度 10，效果嵌套 5；每次解释器调用 4096 gas、每次分发最多 32 事件；最多 32 个未完成计时器。数值、图形和地图尺寸有界。新规则可以追加，但既有规则 ID 不得被静默替换；变形图形应使用新 ID 后切换对象引用。

地图验证检查边界、基本可接近性、玩家位置与结构出口。**不声称证明任意生成谜题一定可解。**实心对象可以是需要操作才打开的门；不会为了“可达性”自动挖穿它。重复操作是否平衡、剧情是否好玩仍需要真实模型与玩家测试。

## 测试

```text
python -m unittest discover -s tests -v
python tools/build_content_fixture.py
godot --headless --path . --script res://tests/content_smoke.gd
```

Python 测试覆盖实际操作开门、历史位置跟随、非枚举目标、自定义战斗、计时器、动态绘图与地表、越界拒绝、级联预算、原子回滚、读档与在线协议拒绝降级。原生验收检查真实 Godot 中的动画像素、模型地图、动作面板和战斗 UI。仓库 CI 包含这些检查。早期验证记录见 [Content Runtime v2 验证](REFRACTOR_TEST_REPORT.md)，当前结果应查看对应提交的 Actions。

## 仍然存在的边界

这是**受控、可编程的 2D JRPG 内容运行时**，不是任意游戏代码执行器。音乐、称谓、面板及资源可由模型数据配置，系统 UI 和播放/渲染实现仍固定。章节世界使用双向连接图及共享目标；战斗仍依赖 hp，启用装备时沿用既有槽位。所有程序原语都有资源限制，不能将配置能力等同于任意游戏系统。完全不复用人物身份、已有物品或底层执行器既没有必要，也会破坏连续性。应减少的是成品玩法和内容模板的复用。
