# Web 真实试玩与 Luna Medium / High 对照

实测于 2026-09-22 至 23 日，整理于 2026-09-23。结论：Medium 明显缩短了这次首个可玩地区的等待，但两局都没有完成整个章节。当前最影响体验的是反复生成修复、预取作废和出口等待；已交付内容的普通行动响应较快。本轮不能证明 Medium 是所有任务平均最快或质量与 High 等价。

## 本次交付

新增本机 Web 前端，复用 Python 权威运行时、存档、规则和动作事务。可以在浏览器创建世界、移动、交互、选择剧情、使用能力和物品，并查看任务、生成进度和重试入口。点击对象会逐步执行普通移动，遇到事件停止。服务启动见 [Web 使用说明](WEB_CLIENT.md)。

本机保留了两局存档，服务重启后保持生成暂停，避免在结束测量后继续消耗额度：

| 存档 | 浏览器地址 | 停留位置 |
|---|---|---|
| `userdata/web-playtest-20260922` | <http://127.0.0.1:58002/> | High，北侧海堤 |
| `userdata/web-medium-20260922` | <http://127.0.0.1:59005/> | Medium，临时码头出口 |

地址依赖本机服务仍在运行。以后可用 `python launch.py --web --port 58002 --data-dir ./userdata/web-playtest-20260922` 恢复 High，Medium 换成对应端口和目录。同一存档只能启动一个服务。旅途中可以调整后续思考等级和请求上限；应用设置会恢复生成。当前默认仍为 High，Medium 已作为正式可选项接通，响应报告的思考等级也会核对。

## 测量口径

两局使用相同的暴雨海镇、灯塔修理员、年轻向导、有限电池与救援时间设定，要求短篇并有明确结局。均使用 ChatGPT 订阅直连、GPT-5.6 Luna、双路地区生成、素材库、900 秒任务时限、最多一次传输补试，每局实际模型请求上限 16。Jev 凭据未加载，本轮没有进行 Jev 在线审查。

每个等级只有一局。High 规划了 7 个地区，Medium 规划了 5 个地区，内容规模和实际选择不完全相同；两局顺序执行，上游网络与负载也不同。这里是项目实测案例，不是有统计把握的模型排名。

“首个可玩地区等待”从启动章节规划计时，包含失败、修复和手动重试前的间隔。“任务活动耗时”累加到首区交付为止的各任务墙钟耗时，排除任务间的人为等待；双路并发请求不重复累加。动作延迟取服务端 `action.completed.milliseconds`，不含浏览器绘制和自动走路节拍。首个输出指回答文字出现，不等于内容已经可以游玩。

全局已知用量：High 输入 156,982、输出 111,690、其中推理 55,942；Medium 输入 97,806、输出 48,599、其中推理 10,420。推理 tokens 是输出的一部分，不能再次相加。Medium 两次失败请求的最终用量未知，因此这些不是其完整消耗，更不等于货币费用。

High 海堤的下一地区制作单次任务又用了 683.203 秒，其中玩法请求本身 469.266 秒、335.297 秒才出现首个回答文字；我在出口约等了 11 分 39 秒才等到 ready。首区本地校验仅约 0.141 秒。优化普通移动或 JSON 本地校验，无法抵消分钟级模型生成与返工。

## 实际玩了什么

### High

从暴雨码头开始，与梅姨及林言交谈，选择较稳妥的撤退计划，学到“临场交涉”；稳定码头灯使电池 5→4，取得航务图并完成两个地区目标。使用交涉使救援窗口 6→5。

等待北侧海堤 ready 后，通过正常出口进入第二个地区。修好潮压表使电池 4→3，学到“潮汐判读”；使用能力使窗口 5→4。听完林言与陈渡的顾虑，选择“先固定闸门，等潮压下降”，窗口 4→3。共完成五个地区目标。保存后重启，位置、资源和完成状态保持一致，世界状态正文哈希不变。

这部分确实存在资源、人物顾虑和行动分支，读数与交涉能支持具体选择。没有发现这 93 次普通动作中的规则异常，也没有发生 ready 地区进入崩溃。但还没有点亮最终灯塔，不把局部目标完成当作整章可解证明。

![High 北侧海堤的实际浏览器画面](../userdata/web-playtest-20260922/high-delivery.png)

### Medium

在临时码头检查无线电，电池 4→3；阅读值班板，完成“确认出发计划”。和岑遥坦白风险并给她一枚电池，电池 3→2，完成“让岑遥加入调查”。其后查看防水电池箱，文字说里面有三枚备用电池，角色选择留在原位；没有拿取选项，也没有实际补充。

抵达淹水仓库区出口后无法继续：仓库报 `undefined sound cue`，旧泵站报 `audiovisual envelope is invalid`，旧信号所的两条请求发生传输失败，任务最终报告三分钟无 SSE 事件。16 次预算用完。47 次已执行动作未出现运行时异常；没有实际进入第二地区。

电池箱没有承诺发放奖励，因此不能叫“奖励丢失”。但资源紧张时只有检查、没有争取或取舍，会减弱玩家自主性。Medium 的两个地区目标可以完成，尚不足以证明后续依赖、资源平衡与最终结局成立。

![Medium 临时码头与出口等待](../userdata/web-medium-20260922/medium-delivery.png)

### 余额耗尽的单独复验

从 High 存档制作隔离副本，通过五次普通“临场交涉”把救援窗口从 5 消耗到 0，没有调用模型。在 0 时付费能力被禁用并显示余额不足，没有免费透支。主存档未受影响。

与此同时，主目标仍显示进行中，没有清晰的失败、补救或恢复提示。由于没有穷尽未生成地区的资源来源，这只证明反馈缺失，不能证明世界绝对无解。

| 原问题 | 本轮结论 |

| 自依赖目标能通过校验 | 七个地区目标实际完成，未遇到对应自锁；自依赖旗标、钥匙、资源及有向门依赖有回归保护。整章没有通关，任意 DSL 的可解性仍非已证明。 |
| 并行一路失败丢掉另一路、漏记 tokens | High 首区定向重试真实复用了视听成果，只增加玩法请求；逐请求用量有记录。世界级错误仍可能退回整区修复，这是剩余的额外浪费。 |
| 非法 JSON 无法发起修复 | 原始文本进入修复请求的回归通过。本轮没有把专门的非法 JSON 故障注入到付费链路，不能称为新的在线复现。 |
| 音频 cue 不一致与整区重做 | 共享约定和责任分支回归通过；在线发现了“合法素材 ID 简写”在组件预检被误拒的另一处问题，已补修，见下文。 |
| 余额不足仍可免费使用技能 | 正常支付和零余额禁用均通过浏览器操作实证；原子扣费及失败回滚回归通过。资源耗尽后的叙事反馈仍需改善。 |

## 实测后追加的修复

这些改动在基线测量结束后落地，未用于改写上述 High / Medium 数据，也没有再发起一轮在线基准。

1. **音频组件与整区解析共用格式归一化。** Medium 仓库视听结果直接引用 `rpg_v1_knife_slice`，属于提示允许的素材库音效简写；原组件预检没有执行整区解析已有的归一化，误报未定义 cue。现在先执行音频格式归一化，再做严格组件校验。使用保存的真实响应回放，通过且原音效保留。整张仓库进一步校验仍发现出口缺少可达空格，不能宣称修完音效就已交付该地区。
2. **规划地区允许无信息的 `destinations: []` 写法。** 两个等级都曾生成空列表，并因此产生额外修复。章节规划已经定义路线时可确定性移除空列表；传统地区的空列表仍拒绝，规划地区擅自填写非空路线也仍拒绝，避免隐藏真实协议冲突。
3. **正式贯通 Medium。** 浏览器、原生连接设置、直连接口、兼容入口、诊断和用量记录一致使用所选等级；上游报告不匹配时拒绝，避免界面写 Medium 实际跑 High。
4. **Web 等待与状态。** 出口区分生成中、失败、暂停和预算耗尽；生成设置可修改后续等级及上限；有余额或条件限制的按钮显示原因。状态序列防止旧响应覆盖新画面，动作出错后不自动重复发送。

## 剩余问题与优先级

| 优先级 | 已观察证据 | 建议与验收方式 |
|---|---|---|
| P1 | High 旧泵站预取耗时 340.094 秒、三次请求，玩家在这期间正常行动 34 步，人物状态变化使任务被判 stale。 | 缩小预取依赖范围，只对该内容真正读取的事实失效；把区域静态内容和到达时人物状态分开。以“生成期间完成无关对话”回放，验证可保留成果且不引入旧剧情。 |
| P1 | High 首区世界级校验 `legacy merchant requires currency` 触发整区修复，成功视听仍被重做。 | 世界级错误也携带结构化责任路径，交回玩法或视听；用原始失败案例验证只替换责任组件，其他组件字节与用量不变。 |
| P1 | Medium 缓存仓库在音频修复后仍报 `director gate must reserve a free reachable cell`。 | 让规划出口的位置和保留空间由确定性地图编译层约束，或把精确坐标冲突交回玩法修复；发布前验证所有入口、出口和必要交互点可达。不要直接放宽可达性校验。 |
| P1 | 首区耗时 13～21 分钟；要求短篇仍规划 5～7 地区，并反复违反协议。 | 给短篇定义可配置的地区与首区复杂度预算，减少一次响应必须同时设计的规则；把高频结构约束转成编译器可检查的模板。用相同冻结规划、多次生成比较首区与整章成功交付耗时。 |
| P2 | “听梅姨核对风险”禁用提示要求靠近，实际条件是该段已经听过。 | 区分距离不足、已完成、缺资源三种原因；优先显示运行时能确定的原因，生成文本只补充剧情。复验完成后的按钮不会引导玩家反复走近。 |
| P2 | 救援窗口降到 0 后，主目标继续进行，没有清晰反馈；Medium 电池箱只有检查，缺少资源取舍。 | 为关键资源定义耗尽后的失败、补救或替代路径，并用合法动作轨迹验证。内容审查增加“是否有有意义选择”，但不能只凭关键词自动改写故事。 |
| P2 | Medium 出口受阻期间导演继续尝试其他候选地区，最终没有交付玩家正在等待的出口。 | 优先保障当前等待目标；保留其他成功组件，在预算不足时解释当前可行路径和剩余工作。与传输故障分别记账，避免把网络失败算作模型推理质量。 |
| P2 | Web 海堤地图存在大块空地、交互物聚集和文字重叠；两局主要通过阅读与点选推进。 | 先修客户端标签布局与地图视野，再评估地图节奏、空间线索和行动分支。Web 尚未完整复刻 Godot 材质、混音与动效，视觉差异不能全部归因于生成模型。 |

更值得先做的是预取复用、定向修复与地图出口约束，再做更多 Medium 样本。基于本例可以把 Medium 用于更快的日常试玩，但还没有证据支持全量替换 High。后续比较应固定规划、选择路径与验收条件，记录失败率、到首区时间、到结局时间和包括修复在内的已知/未知用量；不要只比较一次请求的 token 速度。
